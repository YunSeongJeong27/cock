# 전체 점검 기록 (2026-10-20, 2차)

다른 에이전트가 이 파일만 보고 무엇을 했는지 알 수 있게 남긴다. 설계·결정 기준은 `docs/design.md` 그대로이고, 이 점검으로 바뀐 결정은 없다.

- 작업 위치: Claude 클라우드 서버. 기준 코드 = `claude/cock-repo-agent-setup-o5p2qp` @ 9f3b9a3 (작업 브랜치 `claude/inspiring-fermat-xogd96`)
- 사용자 요청: 기능 하나하나를 프로세스대로, 그리고 "별의별 짓을 하는 판매자·고객"을 가정해서 점검·디버깅하고, 오류·잘못된 코드·비효율을 고치고 테스트. 운영상 한계로 일부러 둔 것(문서에 기록된 것)은 문제 삼지 않음. 구조적 리팩터링이 필요한 것은 고치지 말고 보고만
- 표기: [사실] 직접 실행·테스트로 확인 / [판단] AI 판단

## 1. 어떻게 점검했나

1. 코드 전부 읽기: 백엔드 전 패키지(common, security, seller, groupbuy, order, customer, deposit, comment, export, notify, vision), `V1__init.sql`, 프론트 전 화면(`PublicOrder`, `OrdersTab`, `OrderEditForm`, `DepositTab`, `ScreenshotDeposits`, `CommentsTab`, `PickupTab`, `GroupBuyForm`, `GroupBuyDetail`, `Profile`, `AdminSellers` 등), 기존 테스트 목록
   - DB 칸 길이 ↔ 입력 검사 길이 대조, 목록 안의 null, 숫자 넘침, 기본 예외 응답 모양, N+1 조회, 화면 규칙 ↔ 서버 규칙 대조
2. 탐색 테스트(임시, 커밋 안 함): 이상한 요청을 API 로 보내 상태 코드·본문 확인 (빈 본문, `[null]`, 아주 긴 글자, 1억 원 넘는 금액, 경로에 글자, 없는 주소, 잘못된 메서드, 다른 공구 상품 id, 유선 전화번호, 남의 이름으로 취소 등 약 30가지)
3. 실제 앱 실행 + 브라우저 시나리오 (jar 에 프론트 포함, local 프로필 새 H2 DB, Playwright Chromium. 스크립트는 클라우드 서버 임시 폴더에만 있음)
   - ① 판매자 가입 → 공구 만들기(상품 2·픽업 지점 2·선입금+현장결제·배송비) → 고객(폰 화면) 1인 최대 넘기기·수령 방법 안 고르고 주문 → 주문 → 같은 번호 재주문 경고 → 수정 → 다른 기기에서 "내 주문 찾기"(개인정보 자동 채움 없음 확인) → 남의 이름으로 취소 시도 → 판매자 수동 입금 확정("15,000원" 입력) → 고객 화면 "주문 확정" → 고객 환불 신청 → 판매자 [취소하고 환불] → [환불 완료] → "완료" 1건
   - ② 주문 직후 빠르게/천천히 같은 번호 재주문 → 경고 표시
   - ③ 픽업 주문이 있는 공구에서 픽업 끄기 → 기존 픽업 주문 [주문 변경] → 주문 멈춤(고객 화면 문구, 주문 409) → 다시 받기 → 거래내역 CSV 미리보기·올리기·자동 매칭 2건 확정 → 같은 파일 다시 올리기 → 엑셀(연락처 포함) → 폰 크기 판매자 화면 6곳 가로 넘침 → 주소에 글자(`/seller/group-buys/abc`)
   - ④ 관리자 로그인·판매자 관리 화면 → 댓글 기능 전체 공개 → 댓글 텍스트 붙여넣기(관리자 닉네임, 취소 후 재주문, 전화번호만 있는 댓글, 999개) → 검수·저장 → 새 손님 주문으로 반영 → 고객이 `+82 10-…` 번호·`<script>` 이름·공백 이름으로 주문 → 판매자 "같은 닉네임" 안내
4. 전체 자동 테스트: H2, PostgreSQL 16 둘 다

## 3. 확인했고 문제없던 것 [사실, 위 탐색·브라우저·기존 테스트]

- 고객: 1인 최대(+ 연타·직접 99 입력 → 최대로 고정), 수령 방법 미선택 400, 다른 공구 상품 id 400, 수량 100000 → 400(넘침 없음), 유선번호로 내 주문 찾기 400, 남의 이름·남의 주문번호로 취소 404, `+82` 번호 정규화, `<script>` 이름은 글자로만 보임, 공백 이름 400, 멈춤 중 주문 409·화면에 판매자 문구, 다른 기기 "내 주문 찾기"는 상태만(휴대폰·주소 자동 채움 없음), 확정된 주문 바로 취소 → 환불 신청 안내, 환불 계좌 형식 400
- 판매자: 다른 판매자 데이터 404, 사용 제한·탈퇴, 주문 변경 후 변경 기록 문장(픽업 지점 오기록 없음), 수령 체크·환불 처리 순서 강제, 완료 주문만 삭제
- 입금 대조: 출금·0원 줄 건너뜀, 자동 매칭 2건 확정, 같은 파일 다시 올리면 전부 중복, 업로드 사용 중이면 삭제 불가
- 댓글: 관리자 닉네임 제외, 취소 후 재주문 합산, 전화번호만 있는 댓글은 주문 아님, 999개는 확인 필요, 링크 주문과 같은 닉네임 안내
- 화면: 폰 크기(375px) 고객·판매자 7개 화면 가로 넘침 0, 브라우저 콘솔 오류 없음(의도된 4xx 응답 기록만)
- 엑셀: 연락처 포함 내려받기 200, xlsx

## 4. 고치지 않은 것

### 구조적 리팩터링이 필요한 것 — 사용자 지시대로 손대지 않고 보고만 [판단]
1. 판매자 공구 목록(`GroupBuyService.list`)이 공구마다 그 공구의 **주문 전체**를 읽어 요약 숫자를 계산함 (공구 수 × 주문 수). 공구·주문이 많아지면 목록 화면이 느려짐. 요약용 집계 쿼리(또는 요약 테이블)로 바꾸는 구조 변경이 필요
2. 주문 목록·입금 대조·엑셀이 공구의 주문을 페이지 없이 전부 읽음. 공구당 주문 수(수백 건 수준)에서는 문제없다고 봄. 수천 건이 되면 페이지·집계 구조가 필요
3. `PublicOrderService`(약 600줄)가 화면 조회·주문·본인 확인·취소·환불 신청을 모두 가짐. 기능별로 나누면 읽기 쉬워짐
4. 같은 도우미가 여러 곳에 따로 있음: 이름 비교 `squash`(PublicOrderService·DepositMatcher·BankStatementReader·화면 2곳), `trimToNull`/`blankToNull`(여러 서비스), 칸 길이 숫자(CommentService 200/2000 등). 공통 도우미·상수로 모으면 어긋날 일이 줄어듦
5. `OrderUpdate` 의 픽업 지점 비교가 객체 참조(`!=`) 비교. 지금은 같은 객체가 와서 문제없음을 확인했지만 id 비교가 더 안전
6. 엔티티 getter·서비스 생성자를 손으로 씀 → 이 점검 뒤 사용자 결정으로 Lombok 적용 (별도 커밋, design.md "2026-10-20 Lombok 사용")

### 문서에 결정·한계로 적혀 있어 문제 삼지 않은 것
- 재고로 막지 않음(기본), 댓글 반영은 "다 팔리면 품절"이어도 막지 않음, 고객은 입금자명을 바꿀 수 없음, 요청 제한은 서버 메모리 기반, 이메일 인증 없음, 사용 제한 판매자의 열린 공구도 고객 주문은 받음, 환불 되돌리기 없음 등

- 공구 상세 화면이 공구·요약·주문을 따로 불러서, 서버가 요약을 계산할 때 주문을 한 번 더 읽음: 이번에는 손대지 않음. 처음에 "API 를 합쳐야 해서"를 이유로 적었는데, API 를 바꾸지 말라는 지시는 없었으므로 이유가 안 됨 (2026-10-21 사용자 정정). 고친다면 서비스에서 주문을 한 번 읽어 요약(`GroupBuyService.dashboard(orders)`)·목록을 같이 돌려주는 화면용 응답으로 (요청 3→2, 주문 쿼리 2→1). `/dashboard` API 는 이 화면만 씀 [사실, 검색]. 다음 작업 후보
- `OverlapDeduplicator`(겹침 제거)·`ImageSlicer`: 읽었고 손댈 곳 없음. `CommentOrderParser`(댓글 해석 정규식)는 이번에 줄 단위로 읽지 않음 (정리본 8장 명세대로 만든 것이고 파프리카 픽스처 등 테스트가 있음)
- 화면들의 긴 JSX·인라인 스타일, `DepositTab`·`GroupBuyForm` 등의 try/catch 반복: 화면마다 상태가 달라 공통 함수로 묶어도 짧아지지 않음
- `AliasBook.record` 는 별칭을 공백만 지워 저장하고(대소문자 그대로), 입금 대조(`DepositMatcher`)는 읽을 때 소문자로 맞춤. 그래서 영문 입금자명이 대소문자만 다른 별칭 2개가 다른 고객을 가리키면 대조에서 둘 중 하나만 쓰임 [코드로 확인, 실행해 보지는 않음]. 저장 방식을 바꾸면 별칭 목록 화면에 보이는 이름도 바뀌어서 이번에는 그대로 둠 (영문 입금자명은 드물다고 봄 [판단])
