### 사용자 결정 (2026-10-13 대화)
- 주문 정리표 엑셀의 휴대폰·배송지 열: 버튼 2개 유지 ("기본" / "연락처·배송지 포함") [결정] → 원문 14장 미결 e 해결
- 유료 기간이 끝난 판매자: 자동으로 막지 않고 화면에 "만료" 표시만. 관리자가 "사용 제한"을 켜면 조회만 가능(쓰기 차단), 열린 공구의 고객 주문은 계속 받음 [결정]
- 슈퍼 관리자(윤성) 판매자 관리 화면: 목록·플랜(무료 체험/유료)·유료 만료일·무료 체험 종료일·사용 제한·메모·탈퇴 처리 [결정]
- 은행 거래내역 열: 기본 후보로 자동 인식 → 인식 결과(어느 열을 썼는지) 화면 표시 → 다르면 판매자가 열 이름 직접 지정 → 은행별 열 설정 저장 [결정]

### AI 판단으로 구현한 것 [제안]
- 주문 상태는 주문 단위 필드(customer_order)로 관리. CustomerMark 테이블은 만들지 않음 (인터뷰 결과 3번 반영)
- 같은 연락처 재주문 / 같은 입금자명을 다른 고객이 쓰는 경우: 막지 않고 경고 후 고객이 "확인했어요"를 누르면 주문 (원문 F-3 ①을 경고 방식으로)
- 동호수 칸은 판매자가 켜면 필수 입력. 닉네임은 "주문 받는 방법"에 따라 선택/필수 (2026-10-15 바뀜, 아래 7차)
- 대조: 후보 2명 이상이면 AMBIGUOUS(직접 선택). 1순위 표시(F-3 ③)는 안 함. 판매자는 어떤 입금이든 미입금 주문을 직접 골라 확정 가능
- 확정 취소 시 그 확정이 만든 별칭은 지우고 바꾼 별칭은 원래대로 되돌림 (4차 코드 리뷰에서 고침, 아래). 거래내역 없이 "수동 입금 확정" 가능 (별칭도 저장)
- 같은 공구에 같은 입금(이름·금액·시각 원문 동일)을 다시 올리면 건너뜀
- 입금 시각 변환: "yyyy.MM.dd HH:mm:ss" 등 연도가 있는 형식만 변환, 연도 없는 값("10-08 10:01")은 원문만 저장 (미결 39 유지)
- PDF 거래내역: 안내 문구로 거절 (미결 16 유지)
- 주문 정리표 엑셀(입금콕이 만들어 판매자에게 주는 장부 파일, 은행 거래내역과 별개): 취소 주문은 별도 시트
- 입금 확인 문구 형식: "[공구명] 입금 확인 안내 / ✅ 닉네임(없으면 입금자명) 상품 N개 입금 확인"
- 비전 AI 거절(refusal) 시 대체 모델 자동 재시도(fallback)는 넣지 않음. "거절했습니다, 직접 입력" 안내
- 스크린샷: 한 번에 20장, 장당 10MB, 이미지는 메모리에서만 쓰고 저장 안 함. [?] 가 남으면 저장 불가. API 제한을 넘는 이미지는 서버에서 줄여서 보냄 (4차, 아래)
- 댓글 텍스트 붙여넣기 형식: 한 줄에 "닉네임 | 댓글" / "닉네임: 댓글" / 탭 (우리가 정한 형식. 밴드 복사 텍스트 실제 형식은 미확인)
- 댓글 → 주문 반영: source=COMMENT 주문으로 만들어 입금 대조·수령·엑셀을 그대로 씀. 다시 반영은 이미 반영된 손님은 두고 처음 보는 손님만 추가 (2026-10-15 바뀜, 아래 7차). 결제 방식은 공구가 선입금을 쓰면 선입금, 아니면 현장결제
- 요청 제한: 공개 API·로그인 POST 를 IP 당 분당 60회 + 본인 확인·취소는 (IP+공구)당 10분 20회 (메모리 기반, 서버 1대 기준)
- 로그인 쿠키 SameSite=Lax + /api 쓰기 요청은 X-Requested-With 헤더 필수 (CSRF 방어, 같은 도메인 배포 전제)
- 가입 직후 첫 화면 = "주문서 링크 만들기"
- 판매자 본인 탈퇴 기능 (비밀번호 확인 → 전체 파기)
- 로컬 샘플 데이터: db/local/V1_0_1 (데모 판매자·공구·주문), 로컬 프로필에서만

### 비전 AI 결정 (2026-10-13, 2차)
- 호출 방식: Anthropic Java SDK 직접 호출 → **Spring AI** 로 교체. VisionExtractor 인터페이스는 유지 [결정] (상업 서비스 + 포트폴리오 둘 다 고려)
- Spring AI 버전: **1.1.8** — 1.1.x 가 Spring Boot 3.5 대상, 2.x 는 Boot 4 대상이라 못 씀 [사실, Spring AI GitHub v1.1.8 / v2.0.1 루트 pom 의 spring-boot.version 3.5.15 / 4.1.1]
- starter(자동 설정) 대신 모듈(spring-ai-anthropic, spring-ai-client-chat)을 직접 써서, 키가 없으면 빈을 만들지 않음 [제안]
- 구조화 출력: `AdvisorParams.ENABLE_NATIVE_STRUCTURED_OUTPUT` 으로 네이티브 구조화 출력 켬 [결정]
  - [사실, 소스·로컬 가짜 서버로 확인] Spring AI 1.1.8 은 이때 요청에 `output_format: {type: json_schema, schema}` + 베타 헤더 `structured-outputs-2025-11-13` 를 보낸다
  - [미확인] Anthropic 문서는 `output_format` 을 deprecated(현재는 `output_config.format`)로 표기. 진짜 API 가 claude-haiku-5-5 에서 이 요청을 받아주는지는 API 키로 확인 필요
- 기본 모델: **claude-haiku-5-5** (환경변수 APP_VISION_MODEL 로 변경). 기본은 꺼짐 유지 (APP_VISION_PROVIDER=anthropic + ANTHROPIC_API_KEY 일 때만 켬) [결정]
- Haiku 5.5 대응 [사실, Anthropic 마이그레이션 문서 기준]:
  - temperature 는 1 이 아니면 400 → 1.0 고정 (Spring AI 기본 0.8 이라 명시 필요)
  - thinking 이 기본으로 켜져 응답이 thinking 블록으로 시작할 수 있음 → Spring AI 1.1.8 의 `.entity()` 는 첫 번째 Generation 만 읽어서 실패함 → ThinkingFilterAdvisor 로 thinking Generation 을 걸러냄 [제안]
- 재시도: Spring AI 기본(최대 10회, 긴 대기) 대신 2회 [제안]. 재시도 대상은 Spring AI 기본과 같게 일시 오류(5xx)·연결 오류만 (4xx 는 재시도 안 함). HTTP 시간 제한: 연결 10초, 응답 120초 [제안, 코드 리뷰 반영]
- thinking 만 오고 텍스트가 없는 응답(thinking 도중 max_tokens·거절 포함)은 "빈 결과"가 아니라 그 장 실패로 처리 [제안, 코드 리뷰 반영]
- 캡처 사용량 제한: 판매자별 하루 장수 제한, 기본 30장 (APP_VISION_DAILY_CAPTURE_LIMIT, 0 이면 모두 막음). 날짜는 Asia/Seoul. AI 로 보내기 전에 장수를 먼저 차감(실패해도 되돌리지 않음). 남은 장수보다 많이 올리면 아무것도 차감하지 않고 "오늘 한도 초과, 직접 입력" 안내 + 빈 검수 표 [결정: 제한·기본값·안내 / 제안: 차감 방식]
- AI 가 꺼져 있으면 사용량을 세지 않음 [제안]
- 관리자 화면: 판매자별 캡처 사용 장수(오늘 / 이번 달), 하루 제한 장수 변경(비우면 기본값) [결정]
- DB: V2__capture_usage.sql (seller.daily_capture_limit, capture_usage 테이블) 
- 확인한 것: 단위·통합 테스트(가짜 ChatModel로 네이티브 스키마가 AnthropicChatOptions 에 들어가는지, temperature 1, 이미지 첨부, thinking 필터, 거절 처리), 로컬 가짜 Anthropic 서버로 실제 HTTP 요청 본문 확인
- 남은 확인 [미결]: API 키가 생기면 claude-haiku-5-5 로 실제 동작 확인 (output_format 수용 여부, 실제 캡처 정확도, 장당 비용)

### 전체 점검 (2026-10-13, 3차) — 고친 것
표기: [사실] 테스트·실행으로 확인 / [판단] AI 판단

**설계 문서와 다르게 구현했던 것 → 문서대로 고침**
- 고객 주문 취소: 주문번호까지 요구했음 → 인터뷰 결과 4번대로 "휴대폰 번호 + 입금자명"으로 취소. 취소 가능한 주문이 여러 건이면 목록에서 고름 [사실]
- 1인 최대 수량: 주문 1건 기준이었음 → 같은 사람(휴대폰)의 이 공구 주문 합계 기준 (정리본 5장 "1인 최대수량") [사실]

**개인정보·보안**
- "입금자명 + 뒷4자리" 본인 확인만으로 휴대폰 전체 번호·주소·동호수가 자동 채움으로 노출되던 문제 → 주문을 넣은 기기(또는 휴대폰 전체 번호로 확인한 기기)에만 채움. DB V3 (customer_device.verified_by_order) [사실] → 5차에서 더 좁힘: 그 기기에서 넣은 주문에서만 채움 (아래 5차)
- 본인 확인·취소 요청 제한: (IP + 공구)마다 10분 20회 (뒷4자리 대입 방지). 휴대폰 망 IP 공유를 고려해 공구별로 셈 [판단]
- 요청 제한 메모리 정리 버그(IP 기록이 거의 안 지워짐) 수정 [사실]
- CSRF: SameSite=Lax 에 더해 /api 쓰기 요청은 X-Requested-With 헤더 필수 (프론트가 항상 보냄) [사실]
- 오류 응답: 예상 못 한 오류의 내부 메시지를 응답에 넣지 않음 (include-message: never, 500 은 고정 문구). Spring 기본 예외도 ProblemDetail 로 통일 [사실]
- 카톡 문의 링크: http(s):// 만 허용 (javascript: 링크로 고객 화면에 스크립트가 들어가는 것 방지) [사실]
- 관리자 이메일로 일반 판매자가 먼저 가입해 있으면 관리자로 바꾸지 않고 경고 로그 (가입 시 이메일 인증이 없음 → [미결] 이메일 인증 필요 여부) [사실]
- 사용 제한 중인 판매자도 탈퇴(개인정보 파기)는 가능 [판단]

**데이터 정확성**
- 판매자가 상품을 수정할 때 판매 수량(sold)을 옛 값으로 덮어써 재고가 틀어질 수 있던 문제 → sold 는 원자 UPDATE 로만 변경 (updatable=false) [사실, 테스트]
- 주문·공구는 바뀐 열만 UPDATE (@DynamicUpdate) — 동시에 다른 필드를 고칠 때 서로 덮어쓰는 위험 감소 [판단]
- 거래내역 중복 제거: 날짜만 있는 파일에서 같은 사람이 같은 날 같은 금액을 두 번 입금하면 두 번째가 사라지던 문제 → 개수로 비교 [사실]
- "금액만 일치" 추천: 같은 금액의 연결 안 된 입금이 여러 건이면 추천 안 함 [사실]
- 입금 대조 화면의 주문 고르기 목록에 다른 입금에 추천된 주문도 포함 [사실]
- 취소된 주문의 입금 확정을 취소하면 "환불 필요"도 거둠 [사실]
- 거래 유형 열 값에 "출금"·"지급"이 있으면 제외 (금액이 항상 양수인 은행 형식 대비). 정리본 6-1장은 "이자"만 명시 → 확장 [판단]
- 배송 정보 검사를 경고(같은 연락처 등)보다 먼저 / 입금 확인된 주문의 "입금했어요" 거부 / 이름 비교 시 띄어쓰기 무시 [사실]

옵션(기본 OFF): 고유 금액(주문마다 끝자리 다르게). 인터뷰 후 사용 여부 결정.
2단계:
- 밴드 댓글 스크린샷 → AI 추출 → 검수 → 주문 집계 (8장)
- 댓글 텍스트 붙여넣기
- 카톡 대화 내보내기 파일 파서 (실제 샘플 확보 후에만, 추측으로 작성 금지)
3단계(검토): 실시간 입금 확인 (안드로이드 알림 리스너 / SMS / 외부 API). 착수 전 정책 재조사.
최하: 밴드 API 체험판. 네이버 허용 전에는 운영에서 끔. 기능 플래그 기본 OFF.
하지 않음: 오픈톡 자동 연동, 판매문구 자동 발송, MVP 알림톡/SMS, 무인점포, 프랜차이즈,
상품 발주, 카드결제(PG), 택배사 연동(송장 자동 발급).

4. 고객 화면 (주문서 링크) [결정]
--------------------------------------------------------------------------
4-1. 링크 구조
- 공구마다 공유 링크 1개 (예: /g/{공구토큰}). 주문별 조회 링크는 고객에게 안내하지 않는다.
(주문별 랜덤 토큰은 내부용으로만 둔다)
- 한 화면 구성: 위 "내 주문: … 입금 확인됨 ✅" / 아래 주문서.
다음 주문 때 이전 입력값을 자동으로 채운다.
- 재방문 식별: 첫 주문 시 기기에 쿠키 저장 → 다음 방문 때 같은 사람으로 알아본다.
못 알아보면 "입금자명 + 휴대폰 뒷4자리"로 본인 확인 → 그 기기를 기억.
- 쿠키는 기기·브라우저마다 따로이고, 시크릿 모드나 삭제 시 사라짐 [사실] → 본인 확인으로 찾는다.
- 카카오 로그인은 나중 옵션.
- 취소: 마감 후에는 불가.
4-2. 입력 항목
| 항목 | 구분 |
| 상품별 수량 | 필수 |
| 휴대폰 번호 | 필수 (고객 구분 키, 정규화해서 저장) |
| 입금자명 | 필수 (직접 입력, 닉네임을 기본값으로 쓰지 않음) |
| 수령 방법 | 판매자 설정에 따라 보임 (5장) |
| └ 픽업 지점 | 지점이 2개 이상일 때만 보임 |
| └ 배송: 받는 분, 연락처, | 배송을 고르면 필수. 픽업이면 주소를 받지 않음 |
| 주소 검색 + 상세주소 | |
| 결제 방식 | 픽업 + 선입금·현장결제 둘 다 켜졌을 때만 선택 |
| 닉네임 | 판매자가 켜고 끔 (기본 꺼짐) |
| 동·호수 | 판매자가 켜고 끔 (아파트 공구용) |
| 메모 | 없음 (삭제) |
- 닉네임은 고객 구분용이 아니다 (같은 밴드에 동명이인이 있음) [사용자 확인].
- 주소 검색: 카카오(다음) 우편번호 서비스. 상업적 이용 무료, 키 불필요, 사용량 제한 없음
[사실, postcode.map.kakao.com/guide].
- 배송 정보는 카톡을 거치지 않고 주문서에서 끝낸다.
- 나중에 판매자가 입력 항목을 추가·수정하는 기능을 붙인다 (MVP 이후).
4-3. 완료 화면: 주문번호, 총 금액, 계좌번호(복사 버튼), 입금자명 안내.
선입금일 때만 계좌를 안내한다.
4-4. 재고·어뷰징
- 선착순 한정 수량이므로 원자적으로 처리한다:
UPDATE product SET sold = sold + :q
WHERE id = :id AND (stock_limit IS NULL OR sold + :q <= stock_limit)
→ 영향받은 행 0이면 품절. 취소 시 sold 복구.
- 공개 폼에 IP당 요청 제한. 같은 연락처의 중복 주문은 막지 않고 경고만 표시.

5. 판매자 설정 (공구 만들기) [결정]
--------------------------------------------------------------------------
- 기본: 제목, 설명, 상품 목록(이름, 단가, 재고 한도(선택), 1인 최대수량(선택)),
주문 마감 일시, 입금 계좌(은행·계좌번호·예금주, 판매자 기본값 불러오기)
- 상태: DRAFT → OPEN → CLOSED (마감 시각에 자동 CLOSED)
- 수령 방법: 픽업만 / 배송만 / 둘 다
- 픽업 지점: 여러 개 가능
- 픽업 예약 기능 켜기/끄기: 끄면 고객 화면에 픽업이 안 보임.
댓글로 픽업 예약을 받는 판매자는 2단계(댓글 캡처·텍스트)로 집계.
- 픽업 결제 방식 (픽업이 켜졌을 때만 보임): 선입금 켜기/끄기, 현장결제 켜기/끄기
· 선입금만: 계좌번호와 입금 안내 표시
· 현장결제만: 선택칸 없이 현장결제로 접수
· 둘 다: 고객이 선택
· 둘 다 끔: 저장 불가
· 선입금 주문: 입금 대조 대상. 미입금이면 수령 체크 화면에 "미입금" 경고.
· 현장결제 주문: 입금 대조 제외, "현장결제 예정" 표시, 수령 체크할 때 결제 완료 처리.
- 배송비: 없음 / 고정
- 고객 입력 항목 켜고 끄기: 닉네임, 동·호수
- 카톡 문의 링크: 원하면 주문 화면에 붙임 (선택)
- 관리자 닉네임 (2단계 댓글 집계에서 제외할 이름, 쉼표 구분)

6. 입금 대조 (MVP 핵심)
--------------------------------------------------------------------------
6-1. 입력
- 판매자가 은행앱·인터넷뱅킹에서 거래내역을 직접 내려받아 올린다 (은행에서 직접 가져오지 않음).
- xlsx/xls, csv: CSV는 UTF-8 실패 시 MS949로 재시도. BOM 제거, 따옴표 안 쉼표 처리.
- 은행앱 거래내역 스크린샷 → AI 추출 (7장)
- 헤더 자동 탐지: 위쪽 30줄 안에서 찾는다. 공백을 제거한 뒤 정확히 일치해야 한다.
· 날짜 후보: 거래일시, 거래일자, 거래일, 일시, 날짜, 일자
· 이름 후보: 입금자명, 입금자, 보낸분, 기재내용, 내용, 적요, 받는분/보낸분, 거래내용
· 금액 후보: 입금액, 입금금액, 맡기신금액, 입금(원), 입금 → 없으면 거래금액
(부호 있는 단일 열. 양수만 입금으로 처리)
· 유형 후보: 거래유형, 구분, 거래구분 → 값에 "이자"가 들어가면 제외
· 못 찾으면 판매자가 열을 직접 지정한다.
· 입금액이 0 이하이거나 이름이 빈 줄은 건너뛴다.
- 토스뱅크 엑셀 구조 [사실, 실물 확인]:
· A열은 비어 있고 B열부터 사용. 위쪽에 제목·성명·마스킹된 계좌번호·조회기간·안내문.
· 9~10행 부근 헤더: 거래 일시 | 적요 | 거래 유형 | 거래 기관 | 계좌번호 | 거래 금액 | 거래 후 잔액 | 메모
· 일시 "2025.11.09 00:12:19". 금액은 부호 있는 한 열.
· 유형 값: 모임원송금, 입금, 체크카드결제, 이자입금, 출금
- 토스뱅크 PDF 구조 [사실, 실물 확인]:
· 열: 거래일자 | 구분 | 거래금액 | 거래 후 잔액 | 거래내용
· 일시 "2025-11-09 00:12:19". 거래내용이 길면 두 줄로 넘어감.
· PDF 읽기는 MVP 미정 (미결).
- 나머지 은행 형식은 실물 샘플을 확보한 뒤 테스트한다.
- [제안] 판매자 안내: "토스는 발급할 때 '입금만 + 엑셀'로 받아 올려주세요"

6-2. 대조 규칙
- 대상: 선입금 주문 중 아직 입금 확정이 안 된, 금액 > 0 인 고객 (현장결제 주문은 제외)
- 근거 판정 순서:
0) (주문서) 입금자명 정확히 일치 + 금액 일치 → 최우선 MATCHED 근거
(고유 금액 옵션 ON이면 "금액 정확히 일치 + 후보 1명"이 최우선)
a) 저장된 별칭(입금자명 → 고객키)
b) 입금자명의 한글/영문(2자 이상)이 닉네임에 포함
c) 입금자명의 숫자(3자리 이상, 이어붙인 값 포함)가 닉네임 숫자와 일치
예: "217-1505" → {217, 1505, 2171505}
- 결과:
· MATCHED: 금액 일치 + 근거 있음 + 후보 1명
· SUGGESTED: 근거 있음 + 금액 다름 → "금액 차이 ±N원" 표시
· SUGGESTED: 금액만 일치 + 그 금액의 미입금 고객이 1명뿐
· 나머지는 UNPAID. 관련 없는 입금은 "관련 없는 입금"으로 따로 보여준다.
- 입금 1건은 고객 1명에게만 사용한다.
- 후보가 2명 이상이면 자동 확정 금지. 목록상 첫 번째 사람에게 임의로 추천을 붙이지 말 것
(구 코드에 있던 버그).
- 대조 결과는 저장하지 않는다. 판매자가 "확정"을 눌러야 저장하고, 별칭(입금자명 → 고객)도 저장한다.
다음 공구부터 자동 매칭에 쓰인다 (단골 반복이 많음 [사실, 달콤 사례]).
- 고객 키: 주문서 = 정규화한 휴대폰 번호 / 댓글·텍스트(2단계) = 닉네임

7. 스크린샷 AI 추출 (은행앱: MVP / 밴드 댓글: 2단계, 같은 파이프라인)
--------------------------------------------------------------------------
- 흐름: 여러 장 업로드 → 이미지별 비전 LLM 호출 → JSON 추출 → 겹침 중복 제거 → 검수 화면 → 확정
- JSON 스키마 (LLM에 강제):
댓글: {"comments":[{"author":"꼭지맘 217-1505","content":"1","order":0}]}
은행: {"deposits":[{"name":"김지영","amount":3800,"datetime":"10-08 10:01","type":"입금","order":0}]}
출금은 type="출금"으로 추출하고 코드에서 제외한다.
- 공지·광고·시스템 메시지도 그대로 추출한다. 제외는 우리 코드에서 한다 (밴드 광고·스티커 있음).
- 읽을 수 없는 글자는 "[?]"로 표시하게 한다 (추측 금지).
- 중복 제거: 인접 이미지의 끝과 시작에서 연속으로 같은 구간을 1번만 남긴다.
일부러 두 번 단 댓글과 구분할 수 없으므로 "중복 의심"으로 표시한다.
- 검수 화면: 판매자가 수정·삭제·추가할 수 있다.
- VisionExtractor 인터페이스 + 구현체 1개. API 키는 환경변수.
- 원본 이미지는 추출 후 즉시 삭제 (기본값). 외부 AI 전송은 개인정보 처리위탁이므로
개인정보처리방침에 명시한다.
- 정확도와 장당 비용은 미검증 → 실제 캡처로 먼저 테스트.

8. 댓글 해석 규칙 (2단계용 명세)
--------------------------------------------------------------------------
결과: ORDER / CANCEL / NOT_ORDER / REVIEW(사람 확인)
1) 수량이 아닌 숫자는 같은 길이의 공백으로 가린 뒤 해석한다 (원문 위치를 유지해야 메모가 분리됨):
전화번호 01[016789]-?\d{3,4}-?\d{4} / 동-호 \d{1,4}\s*-\s*\d{3,4} / \d+\s*(?:동|호)
/ 시각 \d{1,2}\s*시(?:\s*\d{1,2}\s*분)?, \d{1,2}\s*분 / 날짜 \d{1,2}\s*(?:일|월)
/ 금액 \d[\d,]*\s*(?:원|만원) / 기타 \d+\s*(?:번째|등|층|차)
2) 숫자 수량: (\d{1,3}(?:\s*[/+]\s*\d{1,3})*)(?:\s*단위)?
단위 = 개|봉지|봉|박스|팩|세트|통|단|묶음|판|kg|키로|병|마리|포기
단위 앞 \s*는 그룹 안쪽에 둔다. 밖에 두면 메모가 잘림 ("1 7시이후 픽업" 버그).
"1/1/1" → 3, "2+1" → 3 (합산)
3) 한글 수량: (한|하나|두|둘|세|셋|석|네|넷|넉|다섯|여섯|일곱|여덟|아홉|열)+단위,
또는 단독 "하나/둘/셋/넷" → 추정 수량과 함께 REVIEW (단위 필수: "주세요"의 '세' 오인 방지)
4) "취소|캔슬": 수량 없으면 CANCEL, 수량 있으면 REVIEW
5) 수량 후보 0개 → NOT_ORDER, 2개 이상 → REVIEW
6) "수정|변경|바꿔|말고" → REVIEW
7) 수량 0 또는 30 초과 → REVIEW
8) 메모 = 원문에서 수량 부분을 뺀 나머지
알려진 한계: "10/8"을 18로 오인 가능.
집계:
- 관리자 닉네임 제외. 시간순 처리: ORDER 합산, CANCEL이면 수량 0 (이후 새 주문은 다시 합산).
- REVIEW는 판매자가 수량을 확정하기 전까지 합계에서 제외. 수동 수량이 있으면 해석보다 우선.
- 잡담만 한 사람은 제외.
- 주문서 링크 주문은 파서를 거치지 않는다.
보강이 필요한 패턴 [사실, 달콤 등 현장 조사 H-3장]:
- 다품목 줄임말("간장1 양념1"), 단위 불일치(세트 상품에 "팩")
- 추가 주문("추가 2개"), 입금 신고("입금했어요", "입금완료")
- 질문형("2박스 구매 되나요"), 상품 지정 없는 취소, 비밀 댓글
→ 처리 규칙은 미결.
기대 결과 픽스처 (파프리카 공구, 1,900원):
꼭지맘 217-1505|1 / 205-1205|1 7시이후 픽업 / 망고맘|1 / 쏠|1 / 신한화|1 / 캐파101동|1 / 신지|1
/ 공구장|(공지, 관리자 제외)
→ 고객 7명, 7개, 13,300원. "205-1205"의 메모 = "7시이후 픽업"

9. 수령 체크·엑셀·대시보드
--------------------------------------------------------------------------

1. 수령 방식
- 배송: 선입금만. 입금은 바로 알 수 없으므로 주문 후 고객에게 "입금하셨습니까?" 확인을 띄움
  (고객 입금 신고 = 확정 아님). 확정은 판매자가 입금내역 대조 후 누름.
- 픽업: 기본값 = 픽업 예약(현장결제). 판매자가 "선입금" 옵션을 켜고 끔.
- 판매자는 배송·픽업을 각각 고객에게 보일지 켜고 끔.
- 입금 대조는 입금 케이스(배송, 선입금 픽업)만. 대조 대상이 아니어도 모든 주문의 상태는 판매자·고객 모두 볼 수 있음.
- 주문 상태 흐름(선입금): 입금 대기 → (고객 입금 신고) → 입금 확인됨(판매자 확정) → 수령 완료
- 주문 상태 흐름(현장결제): 예약됨 → 수령 완료(결제 완료 처리)
2. 쿠키로 고객을 알아보는 범위: 공구 단위 (다른 공구에서는 새 고객)
3. 입금·수령 상태: 주문 단위 (한 고객이 두 번 주문하면 각각 관리)
4. 주문 수정 기능 없음 → 취소 후 재주문 (→ 2026-10-15 바뀜: 판매자는 주문 변경 가능. 위 "7차 판매자 주문 변경" 참고)
- 어느 화면에서든 "주문 취소" 버튼 항상 보임 → 전화번호 + 입금자명 입력 → 취소 상태
- 주문서는 항상 화면 아래에 보이므로 쿠키가 있어도 재주문 가능
- 입금 확정된 주문 취소: 바로 취소 + 판매자 화면 "환불 필요" → 판매자가 "환불 완료" 체크
- 마감 후 취소 불가는 기존대로 (정리본 4-1)

- 사용자: 윤성. 자바 웹 개발자(백엔드+프론트 모두 함). 혼자 기획부터 출시까지 하는
사이드 프로젝트. 목표 = 포트폴리오 + 실제 수익.
- 사용자 응대 규칙 (매우 중요):
1) 모르는 건 "모른다", 애매한 건 "애매하다"고 말할 것.
추측을 사실처럼 말하는 것이 최악. 정확도가 생명.
2) "국내에 없다/존재하지 않는다"는 말은 한국어 검색어 5개 이상
+ 앱스토어/플레이스토어까지 확인한 뒤에만 할 것. 쓴 검색어도 같이 보고.
3) 검색 결과 요약(스니펫)만 보고 답하지 말고 원문 페이지를 끝까지 읽고 답할 것.
4) 판매자/업체가 "스스로 주장한 것"과 "검증된 사실"을 구분해서 말할 것.
5) 코드 예시는 생략 없이 전체로. 변수가 어디서 오는지(선언·주입)까지 다 보여줄 것.
쉬운 실제 예시로 핵심만 설명.
6) 결과물 위주로 짧고 직접적으로. 과장 금지
("키만 넣으면 돌아간다" 같은 검증 안 된 단정 금지).

1. 한 줄 요약
--------------------------------------------------------------------------
밴드·카톡·카페·인스타 등에서 공구를 여는 판매자(공구장)를 위한 웹 서비스.
주문을 모으고(①주문서 링크 / ②댓글 스크린샷 업로드), 고객별 수량·금액을 집계하고,
통장 거래내역 엑셀을 올리면 입금자를 자동으로 대조하고, 수령 체크까지 한다.
플랫폼 API를 쓰지 않으므로 특정 플랫폼 약관에 묶이지 않는다.

2. 여기까지 온 배경 (결정 이력)
--------------------------------------------------------------------------
2-1. 아이디어 탐색 중 탈락한 것들 (다시 제안하지 말 것)
- 크론/배치 모니터링: 수익성 불확실
- 모임 회비/출석/벌금 관리: 보류
- 메뉴 추천(지역 → 식당 메뉴 → 평점순): 크롤링 법적 문제
(네이버 약관상 금지, 야놀자-여기어때 사건 등 민사 배상 판례)
- 장부 사진 → AI → 엑셀, 메모/달력 사진 → CRM 자동등록: 사용자가 탈락시킴
- 모바일 청첩장: 템플릿 디자인 싸움
- 결혼식 하객 사진 QR 공유 + 롤링페이퍼: 국내 기존 서비스 다수
(스냅웨딩, 데어무드 모청스냅, 모두의스냅, 메타브 롤링페이퍼 등)
→ 탈락. 과거에 검색 2~3번만 하고 "국내에 없다"고 잘못 말한 적이 있음
→ 0번의 2)번 규칙이 생긴 이유.

2-2. 채택: 밴드 공구 판매자용 툴 (출발점)
- 근거: 크몽에 "밴드 공구 댓글 주문 집계 + 입금 대조" 맞춤 제작 상품이 있음
https://kmong.com/gig/809136 (판매자: 프로일잘러조씨)
패키지 가격 약 30만~49만원 (스탠다드/디럭스/프리미엄). 리뷰 0, 거래 0.
"한 고객에게 30만원에 판매, 주문 38건/61개 처리" 등은 판매자 본인 주장일 뿐
검증 불가 (같은 판매자의 주장이며, 독립된 두 곳의 수요 증거가 아님).
- 해당 페이지 원문 중 확인된 것:
"밴드 연동은 밴드 공식 Open API로만 진행합니다. 비공식 크롤링·스크래핑은 하지 않습니다."
"상시 연동(PREMIUM)은 밴드 공식 Open API로만 진행"
하위 패키지 준비물: "공구 게시글 주소 또는 댓글을 내보낸 파일",
"카톡 대화 내보내기, 엑셀·구글시트 주문서, 손으로 적은 명단 사진도 됩니다"
- 우리 차별점 구상: 건당 맞춤 제작(30만원+)이 아니라
셀프 서비스 월 구독으로 싸게 제공.

2-3. 밴드 API로 상업 서비스 불가 판정 (2026-10-08, 사용자가 약관 원문 확보)
밴드 개발자 약관 (developers.band.us, 네이버 주식회사, 2023-10-04 시행):
- 제6조 1항: "신청 후 회사의 승인을 거쳐 인증Key를 발급" → 심사 있음
- 제6조 3·4항: 이용 가능 횟수 제한 있음, 초과 시 "제휴 절차" 필요
- 제7조 1항: "비상업적인 목적으로만 이용할 수 있으며, 이용자에게 비용을 청구
하거나 … 회원프로그램을 제공해서는 안됩니다" → 유료 서비스 금지
- 제7조 9항: 취득한 정보를 "복제, 저장(캐시 행위 포함), 가공, 배포" 금지
- 제7조 11항: 다수 클라이언트 아이디로 API 호출 금지
- 제8조 1·2항: 인증Key 타인 제공 금지, 1인 1키
- 제8조 5항: 위반 시 즉시 이용정지 / 제12조 3항: 손해배상 청구 가능
- 제9조 4항: "API를 통해 연동한 결과를 복제 또는 저장하거나 전송할 수 없습니다"
- 약관에 요금 조항은 없음 (무료일 가능성 높지만 "무료" 명시 문구도 없음)
결론: 밴드 API로 댓글을 가져와 저장·집계하고 돈을 받는 것은 약관 위반.
공구장 명의 키로 돌리거나, 키를 여러 개 쓰거나, 크롤링하는 우회도 모두 불가/위험.
→ 사용자 최종 결정: API를 쓰지 않는 ①주문서 링크 + ②스크린샷 업로드 방식으로 진행.
(사용자 확인: 밴드에는 "댓글 내보내기" 기능이 없음)

2-4. "결국 계좌이체 판매자만 쓸모 있다" (사용자 지적, 동의함)
- 가장 시간이 드는 일 = 입금자 찾기 = 계좌이체에서만 생김.
- 카드/간편결제를 쓰는 판매자는 결제 서비스가 주문관리까지 해줌 → 필요 없음.
- 현장결제 + 소량(댓글 8개 수준)은 손으로 해도 됨 → 돈 낼 이유 약함.
- 타깃 = 계좌이체로 받고 주문량이 많고 상품이 여러 개인 공구장.
이런 공구장의 수(시장 규모)는 자료를 못 찾음 → 모름.

5. 제품 범위
--------------------------------------------------------------------------
5-1. 사용자 역할
- 공구장(판매자): 회원가입/로그인. 공구 생성, 주문 확인, 입금 대조, 수령 체크.
- 고객(구매자): 로그인 없음. 주문서 링크에서 주문, 자기 주문 조회/취소.
5-2. 주문 입구 (우선순위 순)
① 주문서 링크 (MVP 핵심)
공구장이 공구를 만들면 공개 링크 생성 → 밴드/카톡/카페/인스타 글에 붙임
→ 고객이 링크에서 주문.
② 스크린샷 업로드 (MVP 2단계)
공구장이 댓글/채팅 화면 캡처(갤럭시 스크롤 캡처 포함) 여러 장 업로드
→ 비전 AI가 (작성자, 내용) 추출 → 공구장이 검수·수정 → 기존 댓글 파서로 집계.
②-b 텍스트 붙여넣기 (이미 구현됨, 보조 수단)
③ 카톡 "대화 내보내기" 텍스트 파일 업로드 (선택, 우선순위 낮음)
카톡에 실제로 있는 기능. 다만 파일 형식이 PC/모바일/OS별로 다를 수 있음
→ 실제 샘플 파일을 확보한 뒤에 파서 작성. 추측으로 작성 금지.
④ 밴드 API 체험판 (우선순위 최하, 7장 참고)
5-3. 공통 기능
- 고객별 집계 (수량, 금액, 메모, 확인필요 건)
- 통장 거래내역 엑셀/CSV 업로드 → 입금 대조 (자동확정 / 추천 / 미입금)
- 입금 확정 시 "입금자명 → 고객" 별칭 저장 → 다음 공구부터 자동 매칭
- 수령(픽업) 체크
- 주문표 엑셀 다운로드
- 대시보드: 총 수량, 총 금액, 입금 완료 수, 미입금 수, 수령 수

6. 상세 기능 명세
--------------------------------------------------------------------------
6-1. 주문서 링크 (①)
공구장 화면 — 공구 만들기:
제목, 설명, 상품 목록(이름, 단가, 재고 한도(선택), 1인 최대수량(선택)),
주문 마감 일시, 픽업 장소/시간 안내(여러 지점 선택지 가능),
배송비(선택: 없음/고정), 입금 계좌(은행, 계좌번호, 예금주) — 판매자 기본값 불러오기,
고객 입력 항목 on/off (동·호수, 연락처, 픽업 지점, 메모)
→ 상태: DRAFT → OPEN → CLOSED (마감 시각 도달 시 자동 CLOSED)
고객 화면 (모바일 우선, 로그인 없음):
상품별 수량 선택, 닉네임(밴드/카톡 닉네임), 연락처(휴대폰), 동·호수(선택),
입금자명(필수, 기본값 = 닉네임 아님, 직접 입력), 픽업 지점, 메모
→ 제출 후 완료 화면: 주문번호, 총 금액, 계좌번호(복사 버튼), 입금자명 안내,
"주문 조회 링크"(조회용 토큰 포함 URL)
→ 주문 조회/취소: 조회 링크 또는 연락처+주문번호. 마감 후 취소 불가.
재고 동시성: 선착순 한정 수량이므로 반드시 원자적 처리.
예: UPDATE product SET sold = sold + :q
WHERE id = :id AND (stock_limit IS NULL OR sold + :q <= stock_limit)
영향받은 행 수 = 0 이면 품절 처리. 취소 시 sold 복구.
어뷰징 방지: 공개 폼에 IP당 요청 제한, 같은 연락처 중복 주문은 경고 표시
(막지 말고 공구장이 판단).

6-2. 스크린샷 업로드 (②)
흐름: 이미지 여러 장 업로드 → 이미지별 비전 LLM 호출 → JSON 추출
→ 겹치는 부분 중복 제거 → 검수 화면 → 확정 → CommentOrderParser → 집계
추출 JSON 스키마 (LLM에 강제):
{"comments":[{"author":"꼭지맘 217-1505","content":"1","order":0}]}
- 공지/광고/시스템 메시지도 author와 함께 그대로 추출
(관리자 제외는 우리 코드에서 처리)
- 읽을 수 없는 글자는 추측하지 말고 "[?]"로 표시하도록 프롬프트에 명시
중복 제거: 스크롤 캡처끼리 위아래가 겹치므로,
인접 이미지 끝/시작에서 연속으로 같은 (author, content) 구간을 찾아 1번만 남김.
같은 사람이 같은 내용을 일부러 두 번 단 경우와 구분할 수 없음
→ 검수 화면에 "중복 의심" 표시.
검수 화면: 추출 결과 표(작성자, 내용, 해석 수량, 상태)를 공구장이 수정/삭제/추가 가능.
LLM 공급자: 인터페이스(VisionExtractor)로 추상화해서 교체 가능하게.
정확도와 비용은 미검증 → 4장의 실제 캡처 3장으로 먼저 정확도 테스트할 것.
개인정보: 캡처에 닉네임·동호수가 있으므로 외부 AI API 전송 = 개인정보 처리위탁.
개인정보처리방침에 명시할 것. 원본 이미지는 추출 후 즉시 삭제 (기본값).
확인 안 된 점: 밴드 일반 이용약관이 "공구장이 자기 밴드 화면을 캡처해 외부 도구에
넣는 행위"를 어떻게 보는지 모름 (개발자 약관과 별개).

6-3. 댓글/텍스트 해석 규칙 (CommentOrderParser — 이미 구현·테스트됨)
결과 타입: ORDER(주문) / CANCEL(취소) / NOT_ORDER(주문 아님) / REVIEW(사람 확인)
1) 수량이 아닌 숫자는 같은 길이의 공백으로 가린 뒤 해석
(원문 위치를 유지해야 메모를 정확히 분리할 수 있음):
전화번호 01[016789]-?d{3,4}-?d{4}
동-호 d{1,4}s*-s*d{3,4}
동/호 d+s*(?:동|호)
시각 d{1,2}s*시(?:s*d{1,2}s*분)? 그리고 d{1,2}s*분
날짜 d{1,2}s*(?:일|월)
금액 d[d,]*s*(?:원|만원)
기타 d+s*(?:번째|등|층|차)
2) 숫자 수량: (d{1,3}(?:s*[/+]s*d{1,3})*)(?:s*단위)?
단위 = 개|봉지|봉|박스|팩|세트|통|단|묶음|판|kg|키로|병|마리|포기
주의: 단위 앞의 s* 를 그룹 밖에 두면 공백을 삼켜서 메모가 잘림
(실제로 났던 버그: "1 7시이후 픽업" → 메모가 "이후 픽업"으로 잘림)
슬래시/플러스는 합산: "1/1/1" → 3, "2+1" → 3
(크몽 판매자 설명 기준. 다품목에서 슬래시가 품목별 수량을 뜻하는지는 미확인)
3) 한글 수량: (한|하나|두|둘|세|셋|석|네|넷|넉|다섯|여섯|일곱|여덟|아홉|열) + 단위,
또는 단독 "하나/둘/셋/넷" → 추정 수량과 함께 REVIEW
(단위 필수: "주세요"의 '세'를 수량으로 오인하지 않기 위해)
4) "취소|캔슬" 포함: 수량 후보 없음 → CANCEL, 수량도 있음 → REVIEW
5) 수량 후보 0개 → NOT_ORDER, 2개 이상 → REVIEW
6) "수정|변경|바꿔|말고" → REVIEW (추정 수량 포함)
7) 수량 0 → REVIEW, 수량 30 초과 → REVIEW
8) 메모 = 원문에서 수량 부분만 뺀 나머지 (공백 정리)
알려진 한계: "10/8" 같은 날짜를 슬래시 합산(18)으로 오인할 수 있음
→ 테스트에 추가하고 개선할 것.

6-4. 집계 규칙 (OrderAggregator — 이미 구현·테스트됨)
- 관리자 닉네임(공구별 설정, 쉼표 구분) 댓글은 제외
- 고객 식별: 작성자 고유키가 있으면 그것, 없으면 닉네임
- 시간순으로 처리: ORDER는 합산, CANCEL이면 그때까지 수량 0
(취소 후 새 주문은 다시 합산)
- REVIEW는 공구장이 수량을 확정(manualQuantity)하기 전까지 합계 제외
- manualQuantity가 있으면 해석 결과보다 우선
- 잡담만 한 사람은 목록에서 제외
- ①주문서 링크 주문은 이미 구조화된 데이터라 파서를 거치지 않음
(OrderItem을 바로 사용)

6-5. 통장 파일 읽기 (BankStatementReader — 이미 구현·테스트됨)
- xlsx/xls (Apache POI WorkbookFactory), csv (UTF-8 실패 시 MS949로 재시도,
BOM 제거, 따옴표 안 쉼표 처리)
- 위쪽 30줄 안에서 헤더 줄 자동 탐지 (공백 제거 후 정확히 일치):
날짜 후보: 거래일시, 거래일자, 거래일, 일시, 날짜, 일자
이름 후보: 입금자명, 입금자, 보낸분, 기재내용, 내용, 적요, 받는분/보낸분, 거래내용
금액 후보: 입금액, 입금금액, 맡기신금액, 입금(원), 입금
- 못 찾으면 공구장이 열 이름을 직접 지정 (ColumnMapping)
- 입금액 0 또는 이름이 빈 줄(출금 줄)은 건너뜀
- 은행별 실제 파일로는 테스트 안 함 → 실제 샘플(국민/신한/우리/하나/농협/카카오뱅크/
토스뱅크 등)을 확보해서 테스트할 것. 은행 API 자동 연동(오픈뱅킹 등)은 개인 사업자가
쓸 수 있는지 확인 안 함 → MVP 범위 밖.

6-6. 입금 대조 규칙 (DepositMatcher — 이미 구현·테스트됨)
대상: 아직 입금 확정 안 된, 금액 > 0 인 고객
근거(nameEvidence) 판정 순서:
a) 등록된 별칭 (입금자명 → 고객키)
b) 입금자명의 한글/영문만 남긴 문자열(2자 이상)이 닉네임에 포함
c) 입금자명 숫자(3자리 이상 묶음, 이어붙인 값 포함)가 닉네임 숫자와 일치
예: "217-1505" → {217, 1505, 2171505}
1단계 MATCHED: 금액 정확히 일치 + 근거 있음 + 후보가 1명뿐
2단계 SUGGESTED: 근거 있음 + 금액 다름 → "금액 차이 ±N원" 표시
3단계 SUGGESTED: 금액만 일치 + 그 금액의 미입금 고객이 1명뿐
나머지 UNPAID. 입금 1건은 고객 1명에게만 사용. 관련 없는 입금은 unmatchedDeposits로.
대조 결과는 저장하지 않음. 공구장이 "확정"을 누를 때만 저장 + 별칭 저장.
①주문서 방식에서는 고객이 입금자명을 직접 적으므로
"입금자명 정확히 일치 + 금액 일치"를 최우선 MATCHED 근거로 추가할 것.
고객 키(공구 간 동일인 식별): ①에서는 연락처(정규화한 휴대폰 번호),
②에서는 닉네임.

7. 밴드 API 체험판 (우선순위 최하 — 맨 마지막에, 여유가 있을 때만)
--------------------------------------------------------------------------
사용자 의도: 무료 체험 용도로 밴드 API를 붙여서 써보게 하는 것.
경고 (반드시 사용자에게 다시 알릴 것):
- 무료 체험이라도 유료 서비스의 유입 경로면 "비상업적 목적"으로 보기 어렵다는 해석이
가능 (제7조 1항). 댓글 저장·가공 금지(제7조 9항, 제9조 4항)는 무료여도 적용됨.
- 따라서 네이버(밴드)에 문의해서 허용 여부를 받기 전에는 운영에서 켜지 말 것.
- 구현한다면 기능 플래그(기본 OFF)로 완전히 분리된 모듈로.
이미 확인된 기술 사실:
- Base URL: https://openapi.band.us
- 댓글: GET /v2/band/post/comments (band_key, post_key, [sort]),
응답 result_data.items[] {comment_key, content, created_at(ms),
author{name, description, user_key, ...}}, result_data.paging.next_params(맵)
- 글 목록: GET /v2/band/posts (band_key, locale)
- 밴드 목록: 내 코드는 /v2.1/bands, 공개 오픈소스(band-mcp-server)는 /v2/bands
→ 어느 쪽이 맞는지 미확인
- 인증: 쿼리 파라미터 access_token 과 헤더 "Authorization: Bearer" 모두 토큰으로 인식
(직접 호출로 확인: 토큰 없음 → error "unauthorized",
가짜 토큰 → error "invalid_token")
- 오류 응답(실측): HTTP 401
{"result_data":{"message":"oauth error","detail":{"error":"invalid_token",
"error_description":""}},"result_code":300}
- 서버는 경로보다 토큰을 먼저 검사함 (없는 경로도 401) → 경로 검증은 진짜 토큰 필요
- 정상 응답 형식은 공개 문서/오픈소스 기준이며 실제 토큰으로는 미검증
- 서비스 등록 화면(사용자 캡처): 개발유형 Open API, 서비스 이름(영문*/한글),
서비스 유형*, Redirect URI*(OAuth용, 쉼표로 여러 개), 이용 목적*, 약관 동의
→ 승인 필요
- 토큰은 "해당 밴드에 가입돼 글을 볼 수 있는 계정" 기준.
다른 사람 계정을 OAuth로 연동할 때 추가 심사가 있는지는 모름.

→ 상태: DRAFT → OPEN → CLOSED (마감 시각에 자동 CLOSED)
고객 화면 (모바일 우선, 로그인 없음):
상품별 수량, 닉네임(밴드/카톡 닉네임), 연락처, 동·호수(선택),
입금자명(필수, 직접 입력), 픽업 지점, 메모
→ 완료 화면: 주문번호, 총 금액, 계좌번호(복사 버튼), 입금자명 안내,
"주문 조회 링크"(조회용 토큰 포함 URL)
→ 주문 조회/취소: 조회 링크 또는 연락처+주문번호. 마감 후 취소 불가.
재고 동시성: 선착순 한정 수량이므로 반드시 원자적으로 처리.
UPDATE product SET sold = sold + :q
WHERE id = :id AND (stock_limit IS NULL OR sold + :q <= stock_limit)
영향받은 행 수 = 0 이면 품절. 취소 시 sold 복구.
어뷰징 방지: 공개 폼에 IP당 요청 제한. 같은 연락처 중복 주문은 막지 말고 경고만 표시.
[v2 선택 아이디어] 고유 금액: 주문마다 끝자리를 다르게 안내 (19,900 → 19,903).
금액만으로 거의 확정 가능. 단점: 고객이 헷갈림, 공구장 정산이 지저분해짐.
이 방식을 쓰는 실제 사례는 찾지 못함(검색 1회) → 공구장 인터뷰로 수용성 확인 후 결정.
기본값 OFF.

5-2. 스크린샷 업로드 (밴드 댓글 / 은행 거래내역 공통 파이프라인)
흐름: 이미지 여러 장 업로드 → 이미지별 비전 LLM 호출 → JSON 추출
→ 겹치는 부분 중복 제거 → 검수 화면 → 확정
→ 댓글이면 CommentOrderParser, 은행이면 Deposit 목록 → 집계/대조
추출 JSON 스키마 (LLM에 강제):
댓글: {"comments":[{"author":"꼭지맘 217-1505","content":"1","order":0}]}
은행: {"deposits":[{"name":"김지영","amount":3800,"datetime":"10-08 10:01",
"type":"입금","order":0}]} ← 출금은 type="출금"으로 추출하고 코드에서 제외
- 공지/광고/시스템 메시지도 그대로 추출 (제외 판단은 우리 코드에서)
- 읽을 수 없는 글자는 추측하지 말고 "[?]"로 표시하도록 프롬프트에 명시
중복 제거: 스크롤 캡처끼리 위아래가 겹침 → 인접 이미지의 끝/시작에서 연속으로 같은
항목 구간을 찾아 1번만 남김. 같은 사람이 일부러 두 번 단 경우와 구분할 수 없으므로
검수 화면에 "중복 의심" 표시.
검수 화면: 추출 결과를 공구장이 수정/삭제/추가 가능.
LLM 공급자: VisionExtractor 인터페이스로 추상화 (교체 가능). 키는 환경변수.
정확도와 장당 비용은 미검증 → 3장의 실제 캡처 3장으로 먼저 테스트.
은행앱 캡처 샘플은 아직 없음 → 사용자에게 받아서 테스트.
개인정보: 캡처에 닉네임·동호수·입금자명·금액이 있음 → 외부 AI API 전송 = 개인정보
처리위탁. 개인정보처리방침에 명시. 원본 이미지는 추출 후 즉시 삭제 (기본값).
확인 안 된 점: 밴드 일반 이용약관이 자기 밴드 화면 캡처 활용을 어떻게 보는지 모름.

5-3. 댓글/텍스트 해석 규칙 (CommentOrderParser — 이미 구현·테스트됨)
결과 타입: ORDER / CANCEL / NOT_ORDER / REVIEW(사람 확인)
1) 수량이 아닌 숫자는 같은 길이의 공백으로 가린 뒤 해석 (원문 위치 유지 → 메모 분리):
전화번호 01[016789]-?d{3,4}-?d{4}
동-호 d{1,4}s*-s*d{3,4}
동/호 d+s*(?:동|호)
시각 d{1,2}s*시(?:s*d{1,2}s*분)? 그리고 d{1,2}s*분
날짜 d{1,2}s*(?:일|월)
금액 d[d,]*s*(?:원|만원)
기타 d+s*(?:번째|등|층|차)
2) 숫자 수량: (d{1,3}(?:s*[/+]s*d{1,3})*)(?:s*단위)?
단위 = 개|봉지|봉|박스|팩|세트|통|단|묶음|판|kg|키로|병|마리|포기
주의: 단위 앞 s*를 그룹 밖에 두면 공백을 삼켜 메모가 잘림
(실제로 났던 버그: "1 7시이후 픽업" → 메모 "이후 픽업")
슬래시/플러스는 합산: "1/1/1" → 3, "2+1" → 3 (크몽 판매자 설명 기준)
3) 한글 수량: (한|하나|두|둘|세|셋|석|네|넷|넉|다섯|여섯|일곱|여덟|아홉|열) + 단위,
또는 단독 "하나/둘/셋/넷" → 추정 수량과 함께 REVIEW
(단위 필수: "주세요"의 '세' 오인 방지)
4) "취소|캔슬": 수량 후보 없음 → CANCEL, 수량도 있음 → REVIEW
5) 수량 후보 0개 → NOT_ORDER, 2개 이상 → REVIEW
6) "수정|변경|바꿔|말고" → REVIEW (추정 수량 포함)
7) 수량 0 → REVIEW, 30 초과 → REVIEW
8) 메모 = 원문에서 수량 부분만 뺀 나머지
알려진 한계: "10/8" 같은 날짜를 18로 오인할 수 있음 → 테스트 추가 후 개선.

5-4. 집계 규칙 (OrderAggregator — 이미 구현·테스트됨)
- 관리자 닉네임(공구별 설정, 쉼표 구분) 댓글 제외
- 고객 식별: 작성자 고유키가 있으면 그것, 없으면 닉네임
- 시간순 처리: ORDER는 합산, CANCEL이면 그때까지 수량 0 (이후 새 주문은 다시 합산)
- REVIEW는 공구장이 수량을 확정(manualQuantity)하기 전까지 합계 제외
- manualQuantity가 있으면 해석 결과보다 우선
- 잡담만 한 사람은 목록에서 제외
- 주문서 링크 주문은 구조화된 데이터라 파서를 거치지 않음

5-5. 통장 파일 읽기 (BankStatementReader — 이미 구현·테스트됨)

5-6. 입금 대조 규칙 (DepositMatcher — 이미 구현·테스트됨)
대상: 아직 입금 확정 안 된, 금액 > 0 인 고객
근거 판정 순서:
a) 등록된 별칭 (입금자명 → 고객키)
b) 입금자명의 한글/영문(2자 이상)이 닉네임에 포함
c) 입금자명의 숫자(3자리 이상, 이어붙인 값 포함)가 닉네임 숫자와 일치
예: "217-1505" → {217, 1505, 2171505}
1단계 MATCHED: 금액 일치 + 근거 있음 + 후보 1명
2단계 SUGGESTED: 근거 있음 + 금액 다름 → "금액 차이 ±N원"
3단계 SUGGESTED: 금액만 일치 + 그 금액의 미입금 고객이 1명뿐
나머지 UNPAID. 입금 1건은 고객 1명에게만 사용. 관련 없는 입금은 unmatchedDeposits.
대조 결과는 저장하지 않음. 공구장이 "확정"을 눌러야 저장 + 별칭 저장.
주문서 링크 방식에서는 "입금자명 정확히 일치 + 금액 일치"를 최우선 MATCHED 근거로 추가.
고유 금액 옵션(5-1)이 켜져 있으면 "금액 정확히 일치 + 후보 1명"을 최우선 근거로.
고객 키: 주문서 방식은 정규화한 휴대폰 번호, 스크린샷/텍스트 방식은 닉네임.

- 참고: 밴드공구비서(9-4)도 API를 "사전심사 승인 전 비활성화" 상태로 두고 있음.
이미 확인된 기술 사실:
- Base URL: https://openapi.band.us
- 댓글: GET /v2/band/post/comments (band_key, post_key, [sort]),
응답 result_data.items[] {comment_key, content, created_at(ms),
author{name, description, user_key, ...}}, result_data.paging.next_params(맵)
- 글 목록: GET /v2/band/posts (band_key, locale)
- 밴드 목록: 내 코드는 /v2.1/bands, 공개 오픈소스(band-mcp-server)는 /v2/bands → 미확인
- 인증: 쿼리 access_token과 헤더 "Authorization: Bearer" 모두 인식
(실측: 토큰 없음 → "unauthorized", 가짜 토큰 → "invalid_token")
- 오류 응답(실측): HTTP 401
{"result_data":{"message":"oauth error","detail":{"error":"invalid_token",
"error_description":""}},"result_code":300}
- 서버가 경로보다 토큰을 먼저 검사 (없는 경로도 401) → 경로 검증은 진짜 토큰 필요
- 정상 응답 형식은 문서/오픈소스 기준, 실제 토큰으로는 미검증
- 서비스 등록 화면(사용자 캡처): 개발유형 Open API, 서비스 이름(영문*/한글),
서비스 유형*, Redirect URI*(OAuth용), 이용 목적*, 약관 동의 → 승인 필요
- 토큰은 "해당 밴드에 가입해 글을 볼 수 있는 계정" 기준.
다른 사람 계정을 OAuth로 연동할 때 추가 심사가 있는지는 모름.

· 페이액션·페이똑딱: 쇼핑몰용 입금확인 → 우리는 공구 주문·픽업까지 한 번에
· 밴드공구비서: 1인 로컬 도구, 입금 대조 없음 → 우리는 다계정 SaaS + 입금 대조
- 가격 [제안, 근거 데이터 없음]: 무료 플랜 + 월 1만~2만원대.
참고 가격대: 공구봇 49,000 / 우리동네주문서 약 100,000 / 페이액션 9,900~ / 페이똑딱 8,900~

10-2. 입금 확인 단계별 강화
MVP : 통장 엑셀/CSV 업로드 (구현됨) + 은행앱 거래내역 스크린샷 → AI 추출 (신규)
선택: 고유 금액 옵션 (5-1), 기본 OFF
3단계: 실시간 확인. 아래 중 택1, 착수 전 재조사 필수
(a) 자체 안드로이드 앱 + 알림 리스너 (RTPay 방식) — 플레이 정책 미확인 (9-7)
(b) 자체 앱 + SMS 수신 (페이똑딱 방식) — 플레이 SMS 권한 정책상 어려울 가능성 (9-7)
(c) 페이액션 프로(33,000원/월, API) 같은 외부 API 연동 — 재판매/다계정 이용 조건 미확인

10-3. 범위 축소 (4장에 반영됨)
MVP = 주문서 링크(단순) + 입금 대조(엑셀 + 은행 스크린샷) + 픽업 + 엑셀/대시보드

기간과 종류(입금만 / 출금만 / 전체), 건수 선택 가능. 이메일·저장·공유.
